# Stage06 DeepDive — 미니게임 통합

## 개요
Stage04(자료구조)+Stage05(알고리즘)를 게임 3종에 통합한다.
단일 씬·단일 스크립트로 돌려 의존성 없이 Play 즉시 확인 가능하다.

## S06_01 타워디펜스
### [S06-01-01] 심화: 웨이브 설계와 Queue
웨이브는 순서 보장 단일 생산자 패턴이라 Queue가 자연스럽다.
보스 난입·웨이브 스킵 같은 요구가 생기면 List(인덱스 삽입)나
우선순위 큐(긴급도)로 교체한다. 교체 기준: "순서 변경이 필요한가?"

### [S06-01-02] 심화: PriorityQueue 개념과 타협
정식 우선순위 큐는 힙 기반 O(log n) 입출이다. 본 데모는 적 수가 적어
OrderBy(O(n log n) 매 타격)를 썼다 — 코드가 짧고 읽기 쉽기 때문이다.
적이 수백 기가 되면 (1) 힙 구조 도입, (2) 타격 주기 분산(프레임 분할),
(3) 거리 버킷(공간 분할) 순으로 최적화한다.

### [S06-01-03] 심화: 풀링 실전 체크리스트
풀은 (1) 상한 설정(무한 증식 방지), (2) 프리팹 공유(메모리 절약),
(3) 상태 리셋 누락 방지(hp/dist/위치 초기화)가 핵심이다.
본 코드의 `GetFromPool`이 3가지를 한 곳에 모은 이유다.
Instantiate spikes는 프로파일러에서 GC Alloc 스파이크로 확인한다.

## S06_02 인벤토리+세이브
### [S06-02-01] 심화: 왜 Dictionary인가
인벤 연산은 id 조회가 99%다. Dictionary O(1) vs List O(n) —
아이템 100종이면 매 프레임 인벤 UI 갱신 시 100배 차이가 난다.
순서가 필요하면(정렬 표시) LINQ OrderBy를 표시 시점에만 쓴다.

### [S06-02-02] 심화: JsonUtility 한계와 래퍼 패턴
JsonUtility는 Dictionary·다형성을 지원하지 않는다.
List<Entry> 래퍼가 정석 우회책이며, Newtonsoft 없이도 충분하다.
버전업(필드 추가) 시旧 세이브와 호환되게 필드는 추가만 하고 삭제하지 않는다.

### [S06-02-03] 심화: 세이브 실패 설계
로드 실패 시 크래시/무한로딩보다 "빈 상태 시작+로그"가 정답이다.
실게임에선 (1) 백업 슬롯, (2) 체크섬, (3) 클라우드 동기화 충돌 해결을
추가한다. PlayerPrefs는 소용량 설정용이며, 대용량은 파일 저장으로 간다.

## S06_03 슬라이딩 퍼즐+BFS
### [S06-03-01] 심화: 상태공간 탐색
보드 문자열 키는 "상태=노드, 이동=간선" 그래프 관점이다.
BFS 첫 방문이 최단수 보장이라 힌트 1수가 최적이다.
9! 전체는 36만 상태 — HashSet<string>으로 수십 MB가 들 수 있어 제한이 필수다.

### [S06-03-02] 심화: 상한 설계 기준
maxDepth/maxNodes는 저사양(모바일) 프레임 예산에서 역산한다.
한 프레임 16ms 안에 못 끝나면 코루틴으로 나눠 돌리거나(점진 탐색),
A*+맨해튼합 휴리스틱으로 탐색량을 줄인다. 본 데모는 즉시 반환+경고 로그를 택했다.

### [S06-03-03] 심화: solvable 셔플
3x3 퍼즐은 역전 수(inversion) 홀짝으로 가부가 갈린다. 랜덤 배치의 절반은 불가.
정답에서 유효 이동만 역추적하는 셔플은 항상 풀리므로 힌트 UX가 깨지지 않는다.
완전 랜덤을 쓰고 싶다면 역전 수 판정 함수를 추가해 불가 배치를 버린다.
